## 第II章 AIに関する指示

### ● 背景

学習の過程で、AIはさまざまなタスクを支援してくれる。AIツールの多様な機能と、それが自分の作業をどう支えられるかを時間をかけて探ってみよう。ただし、常に慎重に扱い、結果を批判的に評価すること。コードであれ、ドキュメントであれ、アイデアであれ、技術的な説明であれ、自分の質問が適切だったか、生成された内容が正確かを完全に確信することはできない。仲間(ピア)は、ミスや見落としを防ぐための貴重なリソースである。

### ● 主なメッセージ

- 👉 反復的・退屈な作業を減らすためにAIを使う。
- 👉 コーディング・非コーディングの両面でプロンプトのスキルを磨く。これは将来のキャリアに役立つ。
- 👉 AIシステムの仕組みを学び、よくあるリスク、バイアス、倫理的問題を予測・回避できるようにする。
- 👉 仲間と協力しながら、技術スキルとパワースキル(ソフトスキル)の両方を伸ばし続ける。
- 👉 完全に理解し、責任を持てるAI生成コンテンツのみを使う。

### ● 学習者のルール

- AIツールを探求し、その仕組みを理解する時間を取ること。そうすることで倫理的に使い、潜在的なバイアスを減らせる。
- プロンプトを書く前に問題をよく考えること。そうすれば、正確な用語を使った、より明確で詳細かつ的確なプロンプトを書ける。
- AIが生成したものは何であれ、体系的に確認・レビュー・疑問視・テストする習慣をつけること。
- 常にピアレビューを求めること。自分だけの検証に頼らないこと。

### ● このフェーズの成果

- 汎用的なプロンプトスキルと、分野特化型のプロンプトスキルの両方を身につける。
- AIツールを効果的に使い、生産性を高める。
- 計算論的思考、問題解決力、適応力、協調性を引き続き強化する。

### ● コメントと例

- 試験や評価など、本当の理解を示さなければならない場面に定期的に遭遇する。準備を怠らず、技術スキルと対人スキルの両方を磨き続けよう。
- 自分の考えを説明し、仲間と議論することで、理解の穴が見つかることが多い。ピアラーニングを優先しよう。
- AIツールはあなた固有の文脈を知らないことが多く、一般的な回答をしがちだ。同じ環境を共有する仲間のほうが、より適切で正確な洞察を提供できる。
- AIは最もありがちな答えを生成する傾向があるが、仲間は別の視点や価値あるニュアンスを提供してくれる。品質チェックポイントとして仲間を頼ろう。

**✓ 良い例:**
> AIに「ソート関数はどうテストすればいい?」と聞く。いくつかのアイデアが得られる。それを試し、結果を仲間とレビューする。一緒にアプローチを改善する。

**✗ 悪い例:**
> AIに関数をまるごと書かせ、プロジェクトにコピペする。ピア評価の際、それが何をしているのか、なぜそうなのか説明できない。信用を失い、プロジェクトに落ちる。

**✓ 良い例:**
> パーサーの設計にAIの助けを借りる。その後、仲間とロジックを一緒に追う。2つのバグを見つけ、一緒に書き直す。より良く、よりきれいで、完全に理解したコードになる。

**✗ 悪い例:**
> プロジェクトの重要部分のコードをCopilotに生成させる。コンパイルは通るが、パイプをどう処理しているか説明できない。評価で根拠を示せず、プロジェクトに落ちる。

|---|---|

| 提出ファイル | `construct.py` |
| 許可されるもの | `sys`、`os`、`site` モジュール、`print()` |

### コンストラクト

> ❓ 「現実とは何だ? 『現実』をどう定義する?」 ― モーフィアス

ルールを曲げることを学ぶ前に、まずコンストラクトを理解する必要があった。現実世界に影響を与えずに訓練できる、安全で隔離された環境だ。データエンジニアリングでは、これを**仮想環境**と呼ぶ。

最初のミッションは、Pythonの仮想環境への理解を示すトレーニングプログラムを作ることだ。マシンがグローバルなPythonインストールを汚染してしまった。作業のために、クリーンで隔離された空間を作る必要がある。

### ミッション概要

`construct.py` というプログラムを作成し、以下を行うこと:

- 仮想環境の中で実行されているかどうかを検出する
- 現在のPython環境に関する情報を表示する
- 仮想環境が検出されない場合、仮想環境の作成・有効化の手順を表示する
- グローバル環境と仮想環境とで、パッケージのインストール場所がどう違うかを示す

> ℹ️ プログラムは仮想環境の内外どちらでも動作し、それぞれの状況で異なる出力をすること。

### 使用例

プログラムのテスト方法の例:

仮想環境の外でテストする場合

```
$> python3 construct.py
# 仮想環境がないことを検出し、手順を表示するはず
```

仮想環境を作成してテストする場合

```
$> python3 -m venv matrix_env
$> source matrix_env/bin/activate
(matrix_env) $> python3 construct.py
# 仮想環境を検出し、詳細を表示するはず
```

> ℹ️ 仮想環境をリポジトリに提出しないこと。レビュー中に必要であれば、新しく作成できるようにしておくこと。

## 第V章 Exercise 1: プログラムのロード

| Exercise 1 | loading |
|---|---|
| ディレクトリ | `ex1/` |
| 提出ファイル | `loading.py`、`requirements.txt`、`pyproject.toml` |
| 許可されるもの | `pandas`、`requests`、`matplotlib`、`numpy`、`sys`、`importlib` |

### プログラムのロード

> 🗺️ 「銃が要る。大量の銃が。」 ― ネオ

レジスタンスの戦士たちが武器を脳にロードする必要があったように、データエンジニアも環境にパッケージをロードする必要がある。ただしマトリックスの即時ダウンロードとは違い、競合を避けるために依存関係を慎重に管理しなければならない。

ミッションは、**pip** と **Poetry** の両方を使ったパッケージ管理の習熟を示すプログラムを作ることだ。外部ライブラリを必要とするデータ分析ツールを構築する。

### ミッション概要

`loading.py` というデータ分析プログラムを作成し、以下を満たすこと:

- データ操作に pandas を使う
- 数値計算と、シミュレーション用の「マトリックスデータ」の生成に numpy を使う。データセットの生成元は numpy でなければならない(ハードコードしたリストや `range()` は不可)。
- 可視化に matplotlib を使う
- pip と Poetry の依存関係管理の違いを示す
- 両方の方式に対応した適切な依存関係ファイルを含める

プログラムは「マトリックスデータ」(サンプルデータでシミュレーションしてよい)を分析し、簡単な可視化を生成すること。

デフォルトでは、マトリックスデータは numpy でシミュレーションすること。外部APIから実データを取得したい場合は requests を使ってもよいが、必須ではない。

### 要件

- `requirements.txt`(pip用)と `pyproject.toml`(Poetry用)の両方を作成する
- 依存関係が不足している場合も、プログラムが適切に(クラッシュせずに)対処すること
- インストール済みパッケージのバージョンを表示する比較関数を含める
- プログラムの出力を通じて、pip と Poetry の違いを示す

> ⚠️ プログラムはどのパッケージが利用可能かを検出し、依存関係が不足している場合は役に立つエラーメッセージを表示すること。

> ℹ️ 例外として、この演習に限り、import エラーに関する flake8 と mypy のエラーは許容される。とはいえ、それらのエラーを回避するための仕組みや実装方法も存在するので、興味があればさらに掘り下げてみよう。

### 使用例

依存関係なしでテストする場合

```
$> python3 loading.py
# 不足している依存関係と、pip / Poetry でのインストール手順を表示するはず
```

pip でインストールする場合

```
$> pip install -r requirements.txt
$> python3 loading.py
# 分析を実行し、可視化を生成するはず
```

Poetry でインストールする場合

```
$> poetry install
$> poetry run python loading.py
# Poetry 環境で分析を実行し、可視化を生成するはず
```

## 第VI章 Exercise 2: メインフレームへのアクセス

| Exercise 2 | oracle |
|---|---|
| ディレクトリ | `ex2/` |
| 提出ファイル | `oracle.py`、`requirements.txt`、`.env.example`、`.gitignore` |
| 許可されるもの | `os`、`sys`、`python-dotenv` モジュール、ファイル操作 |

### オラクル

> 💡 「汝自身を知れ。」 ― オラクル

オラクルがすべてを知っているのは、メインフレームの設定にアクセスできるからだ。現実世界でも、アプリケーションはデータベースの認証情報、APIキー、システム設定といった機密情報に、ハードコードせずにアクセスする必要がある。

最後のミッションは、環境変数と `.env` ファイルを使った安全な設定システムを作ることだ。外部システムに安全に接続するデータパイプラインを構築する。

> ℹ️ `.env` ファイルから環境変数を読み込むには python-dotenv ライブラリを使うこと。目的は設定管理に `.env` ファイルを使う方法を学ぶことであり、独自のパーサーを実装することではない。

### ミッション概要

`oracle.py` というプログラムを作成し、以下を行うこと:

- 環境変数から設定を読み込む
- 開発用の設定に `.env` ファイルを使う
- 開発(development)/本番(production)で異なる設定を示す
- 設定が不足している場合の適切なエラー処理を含める

> ℹ️ 開発/本番の違いをどう示すかは自由に実装してよい。ただし、プログラムをテストした際に、その違いが出力で確認できなければならない。

### 設定の要件

プログラムは以下の設定変数を扱うこと:

- `MATRIX_MODE` ― `"development"` または `"production"`
- `DATABASE_URL` ― データストレージへの接続文字列
- `API_KEY` ― 外部サービス用の秘密鍵
- `LOG_LEVEL` ― ログの詳細度
- `ZION_ENDPOINT` ― レジスタンスネットワークのURL

> ⚠️ 本物の秘密情報を決してバージョン管理にコミットしないこと! `.env` ファイルは `.gitignore` に含めること。その理由を説明できなければならない。

### 使用例

設定なしでテストする場合

```
$> python3 oracle.py
# デフォルト値/設定不足に関する警告を表示するはず
```

`.env` ファイルを使う場合

```
$> cp .env.example .env
$> # .env を自分の値で編集する
$> python3 oracle.py
# .env ファイルから設定を読み込むはず
```

環境変数で上書きする場合

```
$> MATRIX_MODE=production API_KEY=secret123 python3 oracle.py
# .env ファイルより環境変数が優先されるはず
```

## 第VII章 提出とピアレビュー

> 🗺️ 「道を知っていることと、その道を歩むことは違う。」 ― モーフィアス

いつも通り、課題を自分の Git リポジトリに提出すること。ピアレビューでは、リポジトリ内の成果物のみが評価される。ファイル名が正しいか、念のため再確認しておくこと。

ピアレビューでは、以下を示すことになる:

- 仮想環境についての理解と、それがなぜ重要なのか
- 依存関係管理における pip と Poetry の違い
- 環境変数がアプリケーションを安全かつ設定可能に保つ仕組み
- これらの概念を他の学習者に説明する能力

覚えておくこと:目的はコードを動かすことだけではない。これらのツールの**「なぜ」**を理解することだ。データエンジニアリングの現実世界では、これらのスキルがシステムを安全で、保守しやすく、スケーラブルに保ってくれる。

> ℹ️ 「現実世界へようこそ。」 ― モーフィアス
